- **The header refresh button now forces a full refresh, not just prices** (fixed 2026-09-27): before this, tapping the top-right refresh icon called `/api/refresh` → `runCycle(env, {forceQuotes:true})`, which refreshed quotes for everyone but left `refreshTargets`/`refreshWma` staleness-gated (`TARGET_MAX_AGE_H`=20h, only `TARGETS_PER_RUN`=4 per call) — so consensus/fundamentals for most items wouldn't budge no matter how many times you tapped it.   - **`forceTargets` deliberately does NOT also force `refreshWma`** — caught this the same day, right after shipping, when the user (reasonably) worried about hitting the subrequest ceiling with everyday use. The 200WMA changes at most once a week, so forcing it on every tap of a button meant to be usable often would burn budget for a number that's essentially never stale — `refreshWma(env, s, symbols)` is called with no `force` flag here, always following its own weekly gate (`WMA_MAX_AGE_H`) regardless of who triggered `runCycle`. This keeps the header button's real cost to `~4N` subrequests (N quotes + 3N targets, no FMP_KEY) instead of `~5N`, comfortably covering a portfolio up to roughly a dozen items in one tap rather than blowing the ceiling well before that.
  - **The deeper point, for when this comes up again**: Cloudflare's 50-subrequest cap is a hard ceiling per single Worker invocation — sequential vs. parallel fetches inside that one invocation cost exactly the same, so "do it one at a time" only helps if "one at a time" means *spread across separate invocations*, not looped within one. That's already what the 5-minute cron does for consensus/fundamentals (`TARGETS_PER_RUN`=4/tick, tracked via each symbol's `updatedAt`/`failedAt`) and for WMA (`WMA_PER_RUN`=1/tick) — it's a continuous, budget-safe background refresh that needs no user action and already scales to any portfolio size, just gradually. The header/Ajustes "force everything now" buttons are a *convenience for an immediate one-off refresh*, not the thing keeping data fresh day to day — don't conflate the two when explaining this to the user, and don't be tempted to make the cron itself more aggressive to "fix" perceived staleness; the gradual cadence is the correct design, not a workaround.

Fixed via a shared `prioritizeSymbols(s)` helper in `api.js` — `kind === "holding"` items first, everything else after — using `Array.prototype.sort`'s stability (ES2019+ guarantee) so relative order *within* each group is untouched, only the two groups get reordered relative to each other. Used by both `runCycle()` (replacing its old plain `Object.keys(s.items)`) and the `/api/targets/refresh` route (replacing its old plain `Object.keys(s.items)` too, for the "refresh everyone" case) — this is a shared, single-source-of-truth concern; don't reintroduce a second copy of the sort logic, and don't add priority logic inside `refreshTargets`/`refreshQuotes` themselves — those just process whatever `symbols` order they're handed, in order.
- **Forcing "refresh everyone" never over-spends the subrequest budget, even for large portfolios** (added 2026-09-27, right after the two fixes above, once the user mentioned they actually have 20 real holdings): before this, both the header button (`forceTargets`, alongside quotes in the same invocation) and the Ajustes "Actualizar todos los consensos" button (`/api/targets/refresh` with no `symbol`) sliced `.slice(0, force ? symbols.length : TARGETS_PER_RUN)` — i.e. **no cap at all** when forcing everyone, regardless of portfolio size. This wasn't just slow for a big portfolio, it was actively harmful: a symbol whose `fetch()` fails mid-loop because the invocation ran out of subrequests looks *exactly* like a genuine Yahoo failure to `refreshTargets`'s catch block — it gets `failedAt: now`, and the **next several automatic (non-forced) cron cycles then skip that symbol for 6 hours** (`refreshTargets`'s own `failedAt` backoff filter) before retrying. So a well-intentioned "update everything now" tap on a large portfolio could make some symbols wait *longer* than if the user had done nothing, not shorter.
  - Fixed with `safeForceTargetsLimit(alreadySpent = 0)`: returns `Math.max(TARGETS_PER_RUN, Math.floor((MAX_SUBREQUESTS_SAFE - alreadySpent) / YAHOO_TARGET_COST))` — `MAX_SUBREQUESTS_SAFE`=46 (margin under Cloudflare's real 50), `YAHOO_TARGET_COST`=3 (cookie+crumb+quoteSummary per symbol, no-`FMP_KEY` path). `refreshTargets()` gained a `limit` option (`.slice(0, limit ?? (force ? symbols.length : TARGETS_PER_RUN))`) so callers can pass an explicit safe cap instead of the unbounded `symbols.length`.
  - **The two forcing callers pass different `alreadySpent`, because they have different headroom**: `runCycle()` (header button) also spends subrequests on quotes in the *same* invocation, so it passes `quotesSpent` (however many quotes were actually just fetched, capped at `MAX_QUOTES_PER_RUN`); `/api/targets/refresh` (Ajustes button) never touches quotes in its own invocation, so it passes `0` and gets the full ~15-item headroom. Get this right if you touch either path — conflating them either wastes headroom or risks the exact over-spend bug this fix exists to prevent.
  - Net effect: for a 20-holding portfolio (± watchlist), one tap of either "refresh everyone" button now safely completes some prefix of the (holdings-first) list — always all-or-mostly the holdings, per the priority fix above — and whatever didn't fit simply keeps its old `updatedAt`/no `failedAt` penalty, so the ordinary automatic cron picks it up within the next few 5-minute ticks, same as if the user had done nothing at all. No partial-failure backoff, no silent 6-hour stall. This is exactly the "spread the load across time, remember what's done, prioritize what matters" behavior the user asked for by hand — it's just implemented as *bounding what a single tap attempts*, not as a persisted queue (a queue would be genuine added complexity for no behavioral difference, since the cron already resumes on its own).

- **Grid-trading backtest simulator** (added 2026-09-27, user request after asking about a "sell X% up, buy X% down" strategy they'd heard of — this is the classic **grid trading / percentage-band rebalancing** concept): `src/backtest.js` exports a pure `simulateGrid(history, {qty, avg, stepUpPct, stepDownPct, tradePct})` — self-funding by design (only ever buys back with cash already realized from a prior sell, never assumes outside money), so the "strategy" vs "just holding" comparison starts from the same initial investment and is honest. The **reference price is the first close of the simulated window**, not the position's real `avg` cost — the question being answered is "what would this rule have done over the last N months", not "since I bought", so an old holding that's since moved far from `avg` doesn't trigger a pile of trades on day one. History comes from a new `yahooDailyHistory()`/`getPriceHistory()` pair in `sources.js` (same free Yahoo chart endpoint as `yahooQuote`/`yahoo200wma`, daily candles, `range` picked to cover the requested months since Yahoo only accepts round range values like `3mo`/`6mo`/`1y`) — MOCK mode (`mockDailyHistory`) generates a sine-wave price series so the simulator has real grid crossings to show in dev/tests. Wired via a new `GET /api/backtest?symbol=&stepUpPct=&stepDownPct=&tradePct=&months=` route in `api.js` (purely computational — no state mutation, doesn't even call `saveState`); `qty`/`avg` are read server-side from the item already in state (never trusted from the client) and the route 400s if the symbol has no position. Frontend: `backtestSection()`/`renderBacktestResult()`/`wireBacktest()` in `index.html`, rendered as a collapsed-by-default section in `preview()` (only when the item has a position), with its own inputs (up %, down %, trade %, months) and a "Simular" button that calls the route and renders a stats comparison + scrollable trade list. **Always keep the "simulación histórica, no consejo de inversión" disclaimer** in `renderBacktestResult()` — this shows hypothetical past performance, not a recommendation, and should never be presented as one.
  - **Asymmetric up/down thresholds, not one shared `stepPct`** (changed same day, right after shipping the first version): the first cut used one `stepPct` for both the sell trigger and the buy trigger. The user pushed back — a symmetric band almost never re-buys in a sustained uptrend (the price rarely gives back as much as it just gained), so the strategy just bleeds shares on the way up and loses to buy-and-hold *by construction*, regardless of what `stepPct` you pick. Splitting it into `stepUpPct` (how much it must rise to trigger a sell) and a smaller `stepDownPct` (how much it must merely pull back to trigger a re-buy) lets the strategy redeploy cash on minor dips instead of waiting for a full round-trip — the intended shape for trending markets, not just sideways ones. Keep this asymmetry when touching the simulator; don't quietly re-merge the two thresholds back into one.
  - **Do not let the user (or yourself) chase a "profitable" parameter combination by trial and error on one fixed historical window** — that's curve-fitting to noise, not evidence the rule works going forward. If asked to help "make it profitable," the honest answer is about the strategy's structural fit to trending vs. range-bound markets, not a magic `stepUpPct`/`stepDownPct` pair.
- **Next earnings date** (added 2026-10-01, user request): `nextEarningsDate`/`nextEarningsEpsEstimate` on `targets`, same cheap-fundamental pattern as everything else this build — `yahooTargets()` adds the `calendarEvents` module to the same `quoteSummary` call (zero extra subrequests). Yahoo's `calendarEvents.earnings.earningsDate` is usually a **two-date range** (unconfirmed date), so only `[0]` (the earlier/primary one, same as what Yahoo Finance's own UI shows) is kept; `earningsAverage` is the consensus EPS estimate, best-effort (often `null`). Only populated via the Yahoo fallback path, like the other `yahooTargets`-only fields — stays `null` if `FMP_KEY` is ever set, since `fmpTargets` doesn't provide it.
  - Shown as its own "Próximos resultados" section in `preview()` (between "Fundamentales" and "Tus objetivos"): the date plus a "en N días" sub-line, and the EPS estimate when available.
  - `metrics()` derives `earningsDays = Math.ceil((nextEarningsDate - now) / 86400e3)`, **but only when the date is still in the future** — once a reported date passes (stale `targets`, not yet refreshed with the next one), `earningsDays` goes back to `null` rather than showing a confusing negative number; the section's date line itself still shows the stale date with no "en N días" sub in that case.
  - New sort option `"earnings"` ("Días hasta los próximos resultados" in `#sortSel`). **Unlike every other plain-numeric sort key, this one DID need a `sort.js` change**: `sortVal()` normally just reads `m[sortKey]`, but the sort key is `"earnings"` while the actual field on `metrics()` is `earningsDays` (named that way to avoid clashing with a hypothetical `earnings` field) — without a special case this silently returns `undefined` for every item and the whole list falls back to alphabetical, which is exactly the bug the user hit right after this shipped (fixed same day, 2026-10-01). `sortVal()` now has `if (sortKey === "earnings") return m.earningsDays;`, same pattern as the existing `value`/`plAbs` special cases. **If you add another sort key whose `metrics()` field name doesn't match the key 1:1, you need the same special case in `sort.js` — this is not automatic.** `clsEarnings()` colors it red only when `earningsDays <= 3` (imminent-volatility heads-up), not a good/bad judgment like the other color helpers.

**Known runtime gotchas:**
- **Failed ntfy sends now retry automatically instead of being dropped** (added 2026-09-28, right after the fix below confirmed the user was hitting real HTTP 429s from ntfy.sh): root cause turned out to be ntfy.sh's public server rate-limiting **by source IP**, and Cloudflare Workers has no per-customer egress IP — outbound `fetch()` calls leave through Cloudflare's shared IP pool, so this app's tiny volume of alerts can get 429'd by *other, unrelated* Cloudflare customers' traffic exhausting the same shared "visitor" bucket ntfy.sh sees. Not something fixable in this app's own code (confirmed against ntfy's docs: default `visitor-request-limit-burst`=60, `visitor-request-limit-replenish`=5s, per-IP; a dedicated, non-shared bucket requires either a paid ntfy reserved-topic tier or self-hosting). Given the user wanted resilience rather than a paid/infra fix for now: `notify()` in `src/notify.js` now pushes any failed send (`sendNtfy()` returning `{ok:false}`) onto a new `s.retry` queue (`{title, body, tags, priority, symbol, attempts}`), and a new `retryPending(env, s)` — called from `runCycle()` right after the existing quiet-hours `pending` flush — resends everything in that queue once per cron tick (~5 min), incrementing `attempts` on repeated failure and giving up after `MAX_NTFY_RETRIES`=12 (~1h). `retryPending` still respects quiet hours for priority<5 items (same as the original send path), leaving them queued rather than spending an attempt. **`s.retry` is a separate queue from `s.pending`** — `pending` is specifically for the quiet-hours nightly digest (batches >3 into one "N avisos de la noche" message); `retry` always resends items individually with their original formatting, since bundling a daytime rate-limit retry into "avisos de la noche" wording would be actively misleading. Don't merge the two queues/flushes into one — they exist for different reasons and have different batching behavior. A failed send is never truly lost either way: `notify()` always does `s.log.unshift(...)` unconditionally before attempting to send, so the in-app "Alertas" log is complete regardless of ntfy delivery outcome — only the phone push itself can be delayed or (after 12 tries) dropped.
- (Fixed 2026-09-28) `sendNtfy()` used to swallow every failure in an empty `catch {}` and callers had no way to know whether the push to ntfy.sh actually succeeded. This meant `/api/test-notification` always returned `{ok:true}` as long as `NTFY_TOPIC` was configured — regardless of whether ntfy.sh actually accepted the request — so the "Enviar notificación de prueba" button in Ajustes was structurally incapable of ever reporting a real delivery failure. Found this while debugging the user's "las alarmas no me llegan" report (2026-09-28): alerts were logging correctly in-app (`notify()` always does `s.log.unshift(...)` first, unconditionally) but confirmed via `npx wrangler secret list` that `NTFY_TOPIC`/`APP_TOKEN` were both set, and it wasn't quiet hours — so the silent `catch {}` was the prime remaining suspect, hiding whatever ntfy.sh-side problem (bad topic, rate limit, transient failure) was actually occurring. Fixed: `sendNtfy()` now returns `{ok, error?}` — `ok:false` with the real HTTP status or thrown-error message on failure — and `/api/test-notification` forwards that instead of hardcoding `{ok:true}`. The frontend's `#sTest` button also gained a `try/catch` (it had none — an `api()` throw would previously fail with zero visible feedback, no toast at all). **When someone reports "alerts aren't arriving," check the test-notification button's *actual* returned error text first** now that it's trustworthy — before assuming it's a phone-side ntfy/Android issue (wrong topic subscribed, battery optimization killing the background connection, notification permission revoked), which is still the most likely cause once the server confirms it really did get a 2xx from ntfy.sh.
- (Fixed 2026-09-26) `src/notify.js` originally used `escape()`/`unescape()` to build the RFC 2047-encoded ntfy `Title` header. Those legacy globals are not guaranteed in the Cloudflare Workers runtime (`workerd`) — they worked fine locally under Node, so this shipped and silently broke real notifications for a day (the `fetch()` to ntfy.sh threw, and the surrounding `try/catch` swallowed it, so `/api/test-notification` still returned `{ok:true}` with nothing actually sent). Fixed via `encodeTitle()` using `TextEncoder` instead — see `test/notify.test.js` for the regression tests. **Lesson: don't trust that a data/mock-mode test passing means the real Workers runtime will behave the same as Node for anything using older/legacy JS globals** — when in doubt, verify against the actual deployed Worker (`Invoke-WebRequest` from PowerShell, not `curl` — this Windows machine's Git Bash `curl` has an unrelated schannel TLS quirk against this specific Cloudflare edge cert that PowerShell doesn't hit).
- Forcing a full `/api/targets/refresh` (no `symbol`) across a large portfolio can exceed Cloudflare's 50-subrequest-per-invocation limit once `FMP_KEY` is absent (each symbol's Yahoo fallback costs 3 requests: cookie, crumb, quoteSummary — 17+ symbols already blows the budget). The normal cron avoids this via `TARGETS_PER_RUN` (4/cycle); if you ever need to force-refresh everything at once, do it a few symbols at a time.
- **Adding a new field to `targets[sym]` (P/E, PEG, fundamentals, description, whatever's next) does nothing for items the user already has** until that symbol's consensus is re-fetched — `refreshTargets()` only touches stale entries (`TARGET_MAX_AGE_H` = 20h) or forced ones, so existing KV state keeps the old shape (missing the new field, reads as `undefined`/absent in the UI) until the next cron cycle happens to land on it or the user forces it. Hit this exact thing 2026-09-27 right after shipping the PEG/dividend/description round: deploy was 100% correct (verified against the live Worker directly), but the user saw nothing change no matter how many times they reloaded/reopened the PWA — because the problem wasn't caching, it was that their real portfolio's cached target data was simply older than the new fields. **When telling a user a new fundamentals/consensus field shipped, immediately also tell them to hit "Actualizar todos los consensos" in Ajustes (or "Actualizar consenso ahora" per item)** — don't let them go down the service-worker-cache troubleshooting path first; check this cause before that one, since the symptom ("reload doesn't fix it") is identical but the fix is completely different.

## Commands

- `npm install` — install deps
- `npm test` — runs `node --test "test/**/*.test.js"` (the bare `node --test test/` directory form does not work on this Windows/Node setup — always use the glob)
- `npm run dev` — `wrangler dev`, serves the PWA + `/api/*` locally on `http://127.0.0.1:8787`; reads `.dev.vars` (gitignored; already has `APP_TOKEN=dev-token` and `MOCK=1` for local testing without real keys or network calls)
- `npm run deploy` — `wrangler deploy`
- `npx wrangler secret put APP_TOKEN|NTFY_TOPIC|FMP_KEY|FINNHUB_KEY` — set real secrets (only meaningful after `wrangler login`; never commit these)
- Single test file: `node --test test/alerts.test.js` (or any other file path)
- `curl -H "Authorization: Bearer dev-token" "http://127.0.0.1:8787/api/diag?symbol=AAPL"` — exercises every data source directly and reports which succeed; the fastest way to debug source/key issues
- `MOCK=1` (already set in `.dev.vars`) makes `sources.js` return deterministic simulated quotes/targets instead of hitting Yahoo/FMP/Finnhub — used throughout the test suite (`test/api.test.js`, `test/sources.test.js`) via a `FakeKV` in-memory stand-in for `env.KV`, so the whole API can be exercised end-to-end with `node:test` and no network/Miniflare needed.

## Architecture

**Runtime**: `src/worker.js` is a thin entry point with two exports:
- `fetch()` — routes `/api/*` to `handleApi()` (`src/api.js`); everything else falls through to `env.ASSETS.fetch(req)` (static PWA files in `public/`).
- `scheduled()` — cron trigger (`*/5 * * * *`) that calls `runCycle()` (`src/api.js`).

**State** (`src/state.js`): all app state lives in a single JSON document in Cloudflare KV under key `state` (spec §5: `items`, `market`, `targets`, `flags`, `log`, `pending`, `settings`, `rot`, `lastRun`). Every request loads the whole document (`loadState`) and mutating routes/the cron write it back in one `KV.put` (`saveState`) — deliberate, to stay within the free-tier KV write quota (spec §4.4). Never introduce per-symbol KV keys without revisiting that quota reasoning. `cleanItem()` is the single place item shape is validated/normalized; `parseImportLine()` handles the bulk-import line format — note the deliberate rule that a comma can't be both field separator and decimal separator in the same line (semicolon/tab as separator → comma is safe to use as decimal; comma as separator → decimals must use a dot).

**Data sources** (`src/sources.js`, each with a mock fallback under `env.MOCK==="1"`):
- Prices: Yahoo Finance chart endpoint (primary, no key, includes pre/post market) → Finnhub quote (fallback, regular session only).
- Search/autocomplete: Yahoo Finance search (primary) → Finnhub search (fallback).
- Analyst consensus: FMP `price-target-consensus` + `grades-consensus` (primary) → Finnhub `recommendation` → Yahoo `quoteSummary` (needs cookie+crumb dance, see `yahooTargets`). Consensus (and `pe`, best-effort via FMP) refreshes at most once/day per symbol, throttled to `TARGETS_PER_RUN` (4) per cron run.
- `/api/diag?symbol=X` (in `api.js`) calls every source function directly (bypassing MOCK) and reports which succeed — the diagnostic tool the spec asks for in §8.

**Cron cycle** (`runCycle` in `src/api.js`, spec §7):
1. Flush any `pending` notifications held back by quiet hours.
2. If a market might be open (`marketsMaybeOpen`, `src/time.js`, checked in America/New_York and Europe/Madrid local time — note Madrid runs 5-6h ahead, so on a normal weekday the EU window is already open whenever the NY pre-market boundary is crossed; see `test/time.test.js` for how the boundary tests are isolated) — or `forceQuotes`/`MOCK=1` — fetch quotes for a rotating slice of symbols (`MAX_QUOTES_PER_RUN` = 35, rotated via `s.rot`) and evaluate alerts for that slice.
3. Refresh stale analyst targets (independent of market hours).
4. Refresh the EUR/USD rate if stale (`refreshFx`, ~daily — cheap, one extra request regardless of item count).
5. Save state once.

**Alert engine** (`src/alerts.js`): each rule is a boolean condition keyed by `${symbol}:${ruleName}` in `s.flags`, with **hysteresis** via `rule()` — fires once on entering its condition, re-arms only once the price exits with margin (spec §6.7 has the full rule/threshold/priority table). Follow this same fire-once/rearm-with-margin pattern for any new rule. `src/notify.js` handles the actual ntfy push and quiet-hours queuing (00:00–07:00 Europe/Madrid; priority <5 alerts queue in `s.pending` during quiet hours and flush together next cycle).

**Important: bump `public/sw.js`'s `CACHE` version string on every deploy that changes anything in its `SHELL` list** (`index.html`, `sort.js`, manifest, icons). The browser only checks for a new service worker by diffing `sw.js`'s own bytes — if you deploy frontend changes without touching `sw.js`, already-installed clients (the phone PWA *and* a plain Chrome tab on the same origin — the SW controls both) keep serving the stale cached shell indefinitely, even after force-closing and reopening. This bit us once already (2026-09-26): shipped a whole list/EUR redesign, user saw nothing change because `CACHE` was still `"...-v1"`. If a user reports "I don't see the change" after a frontend deploy, check this first before assuming the deploy failed.

**Frontend** (`public/index.html` + `public/sort.js`): vanilla JS/CSS/HTML, no build step, no frameworks. The main script is `type="module"` specifically so it can `import` the sort comparator from `sort.js` — that file exists as its own module purely so `test/sort.test.js` can import the exact same comparator the browser uses (spec §13 requires testing "nulls always sort last"); don't inline it back into `index.html` without keeping that split. Talks only to `/api/*` with a bearer token stored in `localStorage`. All derived metrics (upside to mean/high/low, P/L, position value, EUR conversions, etc.) are computed client-side in `metrics()` — the server never computes or stores these. Sort/filter/tab selection persist in `localStorage`. `public/sw.js` is a minimal service worker: cache-first for the shell (listed in its `SHELL` array — update it when adding a new static asset the app needs offline), network-first/no-cache for `/api/*`.

**Auth**: every `/api/*` route requires `Authorization: Bearer <APP_TOKEN>`; no login system since this is single-user. Secrets (`APP_TOKEN`, `NTFY_TOPIC`, `FMP_KEY`, `FINNHUB_KEY`) are set via `wrangler secret put`, never committed; `.dev.vars` (gitignored) holds the local dev equivalents.

**Icons** (`public/icon.svg`, `icon-192.png`, `icon-512.png`): the PNGs are a placeholder radar/target motif generated programmatically (raw PNG bytes via Node's `zlib`, no image library) rather than designed — fine for personal use, but regenerate/replace with a real design rather than hand-editing pixels if that ever matters.
